# Pi0.5 on the Modalix DevKit

Reference for Physical Intelligence's Pi0.5 (LeRobot `pi05`) bundles: the base
model [`lerobot/pi05_base`](https://huggingface.co/lerobot/pi05_base) and
checkpoints fine-tuned from it with LeRobot.

## Choose your starting point

| You have | Start here | Dataset needed? |
|---|---|---|
| A LeRobot `pi05` checkpoint (base or fine-tuned) | [Compiling](#compiling) | Yes: a LeRobot dataset with the checkpoint's cameras, for calibration and the check fixture. |
| A base model and demonstrations | LeRobot's Pi0.5 fine-tuning recipe | Training happens upstream; PoLiMa starts from the resulting checkpoint. |

A bundle is specific to its checkpoint, camera mapping, task text and precision.

### Fine-tuning for the SO-101

The reference SO-101 bundle uses a checkpoint fine-tuned from
[`lerobot/pi05_base`](https://huggingface.co/lerobot/pi05_base) on 769 training
episodes from
[`Priyakarna/SO101-GreyEraser-PickPlace`](https://huggingface.co/datasets/Priyakarna/SO101-GreyEraser-PickPlace).
The dataset has 961 two-camera demonstrations in total. The checkpoint was
trained for 20,000 steps with batch size 8 and seed 1000:

```bash
lerobot-train \
  --policy.path=lerobot/pi05_base \
  --dataset.repo_id=Priyakarna/SO101-GreyEraser-PickPlace \
  --policy.dtype=bfloat16 \
  --policy.freeze_vision_encoder=true \
  --policy.gradient_checkpointing=true \
  --policy.use_relative_actions=true \
  --policy.push_to_hub=false \
  --batch_size=8 --steps=20000 --save_freq=2000 --seed=1000 \
  --output_dir=outputs/pi05_so101
```

This recipe freezes the vision encoder, trains Gemma and the action expert,
uses relative actions except for the gripper, and uses LeRobot quantile
normalization with learning rate 2.5e-5. Adjust the batch size for the available
GPU memory. Compile `outputs/pi05_so101/checkpoints/last/pretrained_model`.

## What runs where

Pi0.5 reads up to three camera pictures, the robot state and a text instruction,
and predicts 50 actions per plan. It has two halves:

- **PaliGemma** (a SigLIP vision encoder and the 18-layer Gemma-2B language model)
  reads the pictures and the prompt once per plan and leaves its keys and values
  (the "prefix") for the second half.
- **The action expert** (an 18-layer Gemma-300M) turns noise into the 50 actions in
  ten flow-matching steps, attending to the prefix at every step.

Everything with weights runs on the Modalix accelerator (MLA). PaliGemma is
compiled by [LLiMa](https://github.com/sima-neat/llima) (`sima_lmm`): one vision
graph and, per Gemma layer, an attention-input graph, a shared attention graph and
an MLP graph, chained on the device so the hidden state never leaves it. The action
expert is compiled by PoLiMa with the ModelSDK. The prefill writes each layer's
keys and values straight into the expert's cache input, and the ten denoising steps
run as one device program: each step reads the actions from one device buffer and
writes the next ones to the other, with the Euler update compiled into the graph.

The DevKit's processor (APU) only prepares the request (tokenized prompt, resized
pictures, normalized state), uploads it, and reads the 50 actions back.

## Compiling

`polima compile --policy pi05` takes a LeRobot `pi05` checkpoint folder
(`config.json` + `model.safetensors`) and a LeRobot dataset with the same cameras.

### Requirements

| Requirement | Version tested |
|---|---|
| ModelSDK (`model-compiler`) | 2.1.3, with LLiMa (`sima_lmm`) 0.4.0 |
| Pi0.5 export interpreter | Python 3.12, PyTorch 2.8 (CPU), Transformers 5.5, LeRobot 0.6.1 with `[pi]` extras, ONNX, ONNX Runtime |
| Build host | x86_64 Linux; the reference builds used 20 cores and ~250 GB RAM |

Point PoLiMa at the export interpreter with `POLIMA_PI05_PYTHON` or the saved
`paths.pi05_python` setting; `polima doctor` checks it. The export runs on the CPU.
The ModelSDK may use an NVIDIA GPU for quantization statistics
(`MODEL_COMPILER_CUDA_VISIBLE_DEVICES`); the model itself runs only on the DevKit.

### Command

```bash
polima compile --policy pi05 \
    --checkpoint /path/to/pi05_checkpoint \
    --dataset /path/to/lerobot_dataset \
    --camera-map wrist_cam=wrist top_cam=overhead \
    --task "Place the grey eraser in the white basket" \
    --precision w8a16 --output ~/polima-builds/pi05-my-task \
    --check-devkit modalix
```

`--camera-map CKPT_CAM=DATASET_CAM` is needed when the dataset's camera names
differ from the checkpoint's. `--task` sets the instruction used for calibration
and the fixtures (default: the dataset's). `--check-devkit` runs the fixtures on a
DevKit and compares them with LeRobot. A build takes one to two hours on the
reference host, most of it in LLiMa.

| Stage | What it does |
|---|---|
| `export` | Loads the checkpoint, writes the PaliGemma folder LLiMa compiles, the expert as ONNX, calibration rows from the dataset, the per-step conditioning constants, the client files and eight fixtures: requests from frames spread over the dataset, each with its own noise, and LeRobot's own actions for them. |
| `llima` | Compiles vision and the 18 Gemma layers with LLiMa. |
| `compile` | Quantizes and compiles the action expert with the ModelSDK. |
| `bundle` | Packs the ELFs, plan, constants, fixture and client files into one bundle. |
| `check` | Optional (`--check-devkit`): runs eight fixtures on the DevKit and compares them with LeRobot. It passes when the **mean** over the fixtures is inside the precision's envelope (`w8a16`: mean absolute error ≤ 0.03 and cosine ≥ 0.995; `bf16`: ≤ 0.01 and ≥ 0.999), and reports the worst fixture for context. |

`--resume` continues a build directory and keeps finished stages.

### Options

| Option | Values | Notes |
|---|---|---|
| `--precision` | `w8a16` (default), `bf16` | See [precision](#precision). `w8a8` is accepted but not evaluated. |
| `--denoise` | `device` (default), `host` | `host` runs each denoising step as its own device call with the Euler update on the APU (~10 ms slower). |
| `--expert-form` | `nchw` (default), `nhwc` | `nchw` is the expert in GR00T N1.7's DiT form (1×1 convolutions). `nhwc` is kept for comparison; the device loop needs `nchw`. |
| `--expert-weights` | `int8` (default), `int4` | INT4 halves the expert's weight traffic but costs accuracy; not recommended. |
| `--backend` | `llima` (default), `onnx` | `onnx` compiles PaliGemma as PoLiMa's own two-layer graphs: about 4× slower and less accurate. Kept as a baseline. |

## Precision

| `--precision` | Vision and Gemma layers | Action expert |
|---|---|---|
| `w8a16` | INT8 weights | INT8 weights |
| `bf16` | BF16 weights | INT8 weights |

On the MLA, a layer with INT8 weights and BF16 activations does not multiply BF16
activations: it quantizes each layer's input to INT8 on the fly, one scale per
token (LLiMa's `A_BF16_W_INT8`), so `w8a16` behaves like dynamic W8A8. BF16 layers
are numerically equivalent to BF16 on a CPU. The `bf16` build keeps the expert at
INT8 weights because ModelSDK 2.1.3's all-BF16 code for the 18-layer expert
returns non-finite values on the DevKit.

## Performance

The published two-camera W8A16 bundle produces 50 actions with ten denoising
steps. On a Modalix DevKit, 20 measured plans after three warm-ups gave 358.5 ms
p50, 359.1 ms p95 and 360.3 ms p99. Its combined vision-language prefill took
202.39 ms and the ten denoising steps took 155.26 ms in the retained stage
profile.

The eight-fixture comparison with the PyTorch checkpoint passed. Action mean
absolute error was 0.016 overall and 0.037 at the worst timestep. See the
[reference benchmarks](benchmarks.md) for the exact artifact, graph layout,
precision and package size.

## Notes for graph authors

- **RMSNorm must fuse.** ModelSDK fuses `x*x → ReduceMean → Add(eps) → Sqrt → Div →
  Mul(weight)` into one RMSNorm kernel. Written as `x * rsqrt(mean(x²) + eps)` it does
  not fuse: the MLA computes `rsqrt` through an INT8 lookup and the mean as an INT8
  convolution, which cost the expert ~6% relative error per step. The expert uses
  the fusible form (an all-ones weight where the norm has none) and compiles with
  `--no-simplify`, because the ONNX simplifier removes the multiply by ones. Check a
  quantized model with `RMSNormOp` present and no `RsqrtOp`. The fusion needs the
  reduction over the channel axis of the compiled layout (axis 1 for NCHW, the last
  axis for NHWC graphs compiled with `--model-layout NHWC`).
- **Persistent bindings for loops.** The device loop needs an expert ELF with one
  binding per input (`compile_onnx.py persistent`), so each step can bind its own
  conditioning buffer and the two action buffers. A single 113,664-channel input
  trips ModelSDK 2.1.3's large-tensor handling, so the per-step conditioning is a
  `[1, 3072, 37, 1]` tensor (one row per norm) with the same bytes.

## Limitations

- The reference bundle has been run on an SO-101 arm; a controlled physical success rate was not recorded.
- At most three cameras (the prefix must fit one 1024-token LLiMa group).
- Ten denoising steps, as trained.
- `w8a8` (INT8 activations at every graph boundary) has not been evaluated for Pi0.5.
- Checkpoints that enable LeRobot's memory features are refused.
